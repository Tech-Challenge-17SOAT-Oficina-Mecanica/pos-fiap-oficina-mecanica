1. O que estamos montando

Um manifesto declara o estado desejado. O Kubernetes compara esse estado com o ambiente e tenta criar ou ajustar os recursos para alcançá-lo. Ter um YAML válido não garante que existam nodes, permissões AWS ou espaço disponível.

Os recursos da aplicação ficam no namespace oficina. A StorageClass existe no escopo do cluster. O PostgreSQL é interno; o Service da API também é interno na configuração atual.

2. Como ler YAML

SintaxeSignificado
campo: valorAssocia uma chave a um valor. Os nomes dos campos seguem a API do Kubernetes; não são tags HTML.
Indentação com espaçosDefine a hierarquia. Em spec.template.spec, cada nível pertence ao anterior. Não use tabulações.
- name: apiUm item de lista. Um Pod pode conter vários containers; aqui há um container por Pod.
[ReadWriteOnce]Uma lista escrita na forma compacta.
---Separa documentos YAML. postgres.yaml contém um Service e um StatefulSet no mesmo arquivo.
# comentárioTexto de orientação ignorado pelo Kubernetes.
"5432" / 5432String / número. ConfigMap exige strings; portas e quantidades de réplicas são números.

3. Campos comuns

apiVersion: apps/v1
kind: Deployment
metadata:
  name: oficina-api
  namespace: oficina
spec:
  # Estado desejado do recurso
CampoExplicação
apiVersionGrupo e versão da API que reconhece o recurso. v1 é o grupo principal; Deployment e StatefulSet usam apps/v1; HPA usa autoscaling/v2.
kindTipo de recurso: Namespace, ConfigMap, Secret, Deployment, Service, HorizontalPodAutoscaler, StorageClass ou StatefulSet.
metadataIdentificação e organização do recurso.
metadata.nameNome usado por comandos e referências. Mesmo nome pode existir em tipos diferentes, como Deployment e Service oficina-api.
metadata.namespaceNamespace ao qual o recurso pertence. Namespace e StorageClass não têm esse campo, pois têm escopo de cluster.
specEspecificação do estado desejado. Seu conteúdo muda de acordo com o kind. ConfigMap e Secret usam campos próprios em vez de spec.

4. namespace.yaml

apiVersion: v1
kind: Namespace
metadata:
  name: oficina

Cria o espaço lógico oficina. Recursos como Service e StatefulSet precisam desse namespace existente para serem criados nele. Namespace organiza recursos; isolação de rede depende de configurações adicionais, como NetworkPolicy.

Para consultar apenas esse espaço: kubectl get pods -n oficina.

5. configmap.yaml

O ConfigMap oficina-api-config guarda configurações sem segredo. O bloco data é um mapa de strings. Os nomes abaixo são variáveis reconhecidas pela nossa aplicação, e não campos especiais do Kubernetes.

Chave em dataValor e finalidade
DB_HOST: "postgres"DNS do Service do banco no mesmo namespace. localhost apontaria para o próprio Pod da API.
DB_PORT: "5432"Porta do PostgreSQL.
DB_NAME: "oficina"Nome do banco; também alimenta POSTGRES_DB no StatefulSet.
SMTP_HOSTServidor SMTP. Vazio deixa esse canal desligado na configuração atual.
SMTP_PORT: "1025"Porta do servidor SMTP, quando utilizado.
SMTP_USUARIOIdentificação do usuário SMTP; a senha fica no Secret.
EMAIL_REMETENTENome e endereço usados como remetente dos e-mails.
NOTIFICACAO_INTERVALO_SEGUNDOS: "30"Intervalo entre ciclos do processamento de notificações. Deve ser positivo.
NOTIFICACAO_LOTE: "20"Quantidade de notificações processadas por lote.
CAPACIDADE_DIARIA_OS: "0"Configuração de capacidade da oficina; zero desabilita a contribuição da fila na estimativa de entrega.
ConfigMap usado como variável de ambiente é lido na criação do container. Alterar o ConfigMap não atualiza automaticamente as variáveis dos containers existentes; é necessário recriá-los por rollout.

6. secret.yaml — estrutura, sem valores reais

apiVersion: v1
kind: Secret
metadata:
  name: oficina-api-secret
  namespace: oficina
type: Opaque
stringData:
  DB_USER: "<usuario>"
  DB_PASSWORD: "<senha>"
  JWT_SECRET: "<chave>"
Campo / chaveExplicação
type: OpaqueSecret genérico com chaves definidas por nós.
stringDataPermite informar strings sem codificar manualmente em base64. O servidor converte para data. Base64 é codificação, não criptografia.
DB_USER, DB_PASSWORDCredenciais usadas pela API e pela inicialização do PostgreSQL.
JWT_SECRETChave de assinatura/verificação de JWT; deve ser consistente entre as réplicas da API.
SMTP_SENHASenha do canal SMTP, quando habilitado.
RESEND_API_KEYCredencial do serviço de envio Resend, quando utilizado.
DATABASE_URL opcionalConexão completa, que tem prioridade sobre as variáveis DB_* na API. Deve apontar para o banco correto; caracteres reservados na senha precisam de codificação de URL.
O arquivo local é ignorado pelo Git e não teve seus valores copiados para este guia. Secrets do GitHub Actions não criam Secrets Kubernetes automaticamente. Não aplique os marcadores deste exemplo como credenciais.

7. deployment.yaml — API

O Deployment mantém os Pods da API e coordena a troca de versões por meio de ReplicaSets. O modelo de cada Pod está em spec.template.

Caminho em specValor e comportamento
revisionHistoryLimit: 3Mantém até três ReplicaSets antigos para rollback; não significa três Pods em execução.
minReadySeconds: 5O Pod deve permanecer pronto por cinco segundos antes de ser considerado disponível pelo Deployment.
progressDeadlineSeconds: 300Prazo para detectar falta de progresso no rollout. Reporta falha; não executa rollback automático.
strategy.type: RollingUpdateTroca gradualmente os Pods da versão anterior pelos da nova versão.
strategy.rollingUpdate.maxUnavailable: 0Durante a atualização, não reduz intencionalmente a disponibilidade abaixo do número desejado. Não protege contra falhas externas.
strategy.rollingUpdate.maxSurge: 1Permite um Pod extra durante o rollout. O cluster precisa ter capacidade para esse Pod.
selector.matchLabels.appDefine quais Pods pertencem ao Deployment: app: oficina-api. Deve corresponder aos labels do template.
template.metadata.labels.appEtiqueta atribuída aos Pods; o Service também usa essa etiqueta para encontrá-los.
replicas ausenteEvita reaplicar uma contagem fixa sobre a escala do HPA. Sem HPA, um Deployment novo assume uma réplica por padrão.

Dentro de spec.template.spec

CampoExplicação
automountServiceAccountToken: falseNão monta automaticamente o token de acesso à API Kubernetes no Pod. Não interfere na assinatura JWT da aplicação.
containersLista de containers do Pod; há um chamado api.
containers[].nameNome do container, usado em comandos como logs e atualização de imagem.
image: oficina-api:v1Imagem atual do manifesto local. No EKS deve ser substituída pelo endereço ECR e a tag SHA publicados pelo CI.
imagePullPolicy: IfNotPresentBaixa a imagem se ela ainda não estiver no node. Tags por commit evitam reutilizar uma versão antiga sob a mesma tag.
ports[].name: httpNome simbólico da porta, referenciado pelo Service e pelas probes.
ports[].containerPort: 8080Documenta a porta do container. Não abre acesso externo e não faz a aplicação escutar por si só.
envFrom[].configMapRef.nameImporta todas as chaves de oficina-api-config como variáveis de ambiente.
envFrom[].secretRef.nameImporta as chaves de oficina-api-secret. O recurso precisa existir no mesmo namespace.
resources.requests.cpu: 100mReserva de agendamento de 0,1 vCPU. 1000m corresponde a uma vCPU.
resources.requests.memory: 128MiQuantidade de memória usada no cálculo de agendamento. Não é um limite máximo.
resources.limits.cpu: 500mTeto de 0,5 vCPU; uso excessivo pode sofrer throttling.
resources.limits.memory: 256MiTeto de memória; ultrapassá-lo pode causar encerramento por OOM.

Probes: três perguntas diferentes

BlocoO que verifica e o efeito
startupProbeA API terminou de iniciar? Verifica /health a cada 2 s, timeout de 2 s e tolerância de 30 falhas consecutivas. Enquanto não passa, adia liveness e readiness. Falhas até o limite reiniciam o container.
livenessProbeA aplicação continua viva? Verifica /health a cada 10 s, timeout de 2 s, limite de 3 falhas; pode reiniciar o container.
readinessProbeA aplicação pode receber tráfego? Verifica /ready a cada 5 s, timeout de 2 s, limite de 3 falhas. Em falha, o Pod deixa de ser elegível para tráfego normal do Service, sem reinício por essa probe.
httpGet.path / httpGet.portCaminho HTTP consultado no Pod e porta de destino, aqui o nome http.
periodSecondsIntervalo entre verificações.
timeoutSecondsTempo máximo de cada tentativa.
failureThresholdQuantidade de falhas consecutivas necessária para considerar a probe malsucedida.
O comentário local sobre GHCR está desatualizado em relação à decisão de publicar no ECR. Este guia descreve a configuração atual e a adaptação necessária; não altera o Deployment.

8. service.yaml — endereço da API

spec:
  type: ClusterIP
  selector:
    app: oficina-api
  ports:
    - name: http
      port: 80
      targetPort: http
      protocol: TCP
Campo em specExplicação
type: ClusterIPCria um endereço interno estável. Não provisiona LoadBalancer público.
selector.appBusca os Pods com app: oficina-api. O vínculo é por label, não pelo nome do Deployment.
ports[].nameNome da porta do Service.
ports[].port: 80Porta pela qual os clientes internos acessam o Service.
ports[].targetPort: httpEncaminha à porta chamada http do Pod, que corresponde a 8080.
ports[].protocol: TCPProtocolo de transporte utilizado.

Exemplo de caminho: oficina-api:80 → Pod da API:8080. Para testes locais com o cluster acessível: kubectl port-forward -n oficina service/oficina-api 8080:80.

9. hpa.yaml — escala horizontal

O HPA muda a quantidade de Pods da API. Ele não cria nodes EC2 e não escala o PostgreSQL.

Campo em specExplicação
scaleTargetRefReferência ao recurso escalado. Seus campos apiVersion: apps/v1, kind: Deployment e name: oficina-api identificam o Deployment no mesmo namespace.
minReplicas: 2Mantém no mínimo dois Pods da API, mesmo com pouca carga.
maxReplicas: 5Permite até cinco Pods. Capacidade insuficiente nos nodes pode deixar novos Pods em Pending.
metricsLista das métricas utilizadas. Aqui há CPU e memória.
metrics[].type: ResourceIndica uma métrica de recurso computacional do Pod.
resource.nameRecurso medido: cpu ou memory.
target.type: UtilizationExpressa o alvo como percentual do request, e não do limit ou da capacidade total do node.
averageUtilization: 70 (CPU)Alvo médio de 70% de 100m: aproximadamente 70m por Pod nesta configuração.
averageUtilization: 80 (memória)Alvo médio de 80% de 128Mi: aproximadamente 102,4Mi por Pod.
behavior.scaleDown.stabilizationWindowSeconds: 300Considera recomendações anteriores em uma janela de cinco minutos para evitar reduzir réplicas por quedas muito breves de carga.

Com várias métricas, o HPA normalmente escolhe a maior quantidade de réplicas recomendada. Precisa de métricas disponíveis, geralmente pelo Metrics Server.

10. postgres-storageclass.yaml — como criar o disco

A StorageClass descreve como provisionar armazenamento. Ela sozinha não cria nem reserva um disco EBS.

CampoValor e significado
apiVersion: storage.k8s.io/v1API de configuração de armazenamento.
kind: StorageClassReceita de provisionamento, com escopo do cluster.
metadata.nameoficina-postgres-gp3, referenciada pelo PVC.
provisioner: ebs.csi.aws.comDriver EBS CSI convencional. Precisa estar instalado e autorizado a operar EBS; é diferente do provisionador do EKS Auto Mode.
parameters.type: gp3Tipo de volume SSD EBS escolhido.
parameters.encrypted: "true"Solicita criptografia do volume em repouso. Não é a configuração de TLS da conexão PostgreSQL.
reclaimPolicy: RetainAo liberar o volume por exclusão do PVC, preserva o PV e o disco para recuperação manual. O armazenamento continua podendo gerar cobrança.
volumeBindingMode: WaitForFirstConsumerAdia a escolha/provisão do disco até haver um Pod consumidor, levando em conta sua topologia. EBS está vinculado a uma zona de disponibilidade.
allowVolumeExpansion: truePermite solicitar aumento pelo PVC se o driver suportar. Não permite reduzir o disco; alterar só o template do StatefulSet não expande um PVC já existente.

Primeiro documento: Service postgres

Campo em specExplicação
clusterIP: NoneService headless: não cria IP virtual; a resolução DNS aponta aos endpoints dos Pods. É útil para a identidade de rede do StatefulSet.
selector.app: oficina-postgresEncontra o Pod do banco por sua etiqueta.
ports[].name: postgresNome da porta do Service.
ports[].port: 5432Porta usada pelo cliente PostgreSQL.
ports[].targetPort: postgresReferencia a porta nomeada postgres do container, também 5432. O protocolo omitido assume TCP.

Segundo documento: StatefulSet oficina-postgres

Campo em specExplicação
serviceName: postgresService que fornece a identidade de rede. O Pod recebe nome estável oficina-postgres-0.
replicas: 1Um servidor PostgreSQL. Aumentar esse número não configura replicação de banco automaticamente.
selector.matchLabels.app / template.metadata.labels.appDevem corresponder: oficina-postgres. Conectam o controlador aos Pods e ao selector do Service.
template.specModelo de configuração do Pod, assim como no Deployment.
automountServiceAccountToken: falseDispensa o token da API Kubernetes dentro do Pod do banco.
terminationGracePeriodSeconds: 60Tempo de encerramento gracioso antes de o Kubernetes forçar a parada do container.
containers[].name: postgresNome do container dentro do Pod.
image: postgres:16-alpineDistribuição oficial PostgreSQL 16 sobre Alpine, alinhada ao ambiente de desenvolvimento.
ports[].name / containerPortNome postgres, porta 5432; referenciados pelo Service.

env: variáveis individuais com referências

Campo / variávelExplicação
env[].nameNome da variável dentro do container.
valueFrom.configMapKeyRefLê uma chave específica do ConfigMap. name identifica o recurso; key identifica o campo.
POSTGRES_DBRecebe DB_NAME de oficina-api-config. Define o banco inicial ao inicializar um diretório vazio.
valueFrom.secretKeyRefLê uma chave específica do Secret, com os campos name e key.
POSTGRES_USERRecebe DB_USER de oficina-api-secret. Cria o usuário inicial com privilégios de superusuário na imagem oficial.
POSTGRES_PASSWORDRecebe DB_PASSWORD do mesmo Secret; define a senha inicial desse usuário.
PGDATA / valueValor literal /var/lib/postgresql/data/pgdata. Usa subdiretório do disco para não conflitar com diretórios do sistema de arquivos, como lost+found.
POSTGRES_DB, POSTGRES_USER e POSTGRES_PASSWORD inicializam um diretório vazio. Alterar o Secret depois não muda automaticamente a senha de um banco existente. Neste MVP, API e banco compartilham o usuário inicial; uma conta de aplicação com privilégios menores é um passo posterior.

Recursos e probes do banco

CampoExplicação
resources.requestsCPU 100m e memória 256Mi para o agendamento.
resources.limitsCPU "1" (uma vCPU) e memória 512Mi. Carga elevada pode exigir ajuste.
startupProbe.exec.commandExecuta sh -c 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'. A shell expande as variáveis. Verifica aceitação de conexões; não comprova migrations nem credenciais da API.
startupProbe.periodSeconds: 5 / failureThreshold: 60Janela aproximada de cinco minutos para inicialização. Timeout omitido assume 1 s.
readinessProbe.exec.commandRepete pg_isready para controlar prontidão após o início.
readinessProbe.periodSeconds: 5 / timeoutSeconds: 3Checagem a cada 5 s, com até 3 s por tentativa. O limite de falhas omitido assume 3.

volumeMounts e volumeClaimTemplates

volumeMounts:
  - name: dados
    mountPath: /var/lib/postgresql/data

volumeClaimTemplates:
  - metadata:
      name: dados
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: oficina-postgres-gp3
      resources:
        requests:
          storage: 2Gi
CampoExplicação
volumeMounts[].name: dadosConecta o diretório do container ao volume criado pelo template com o mesmo nome.
mountPathPonto de montagem dentro do container. O PGDATA está dentro dele.
volumeClaimTemplatesModelo para criar um PVC por réplica do StatefulSet. Não está dentro de template.spec; pertence ao spec do StatefulSet.
metadata.name: dadosGera o PVC dados-oficina-postgres-0 para o primeiro Pod.
accessModes: [ReadWriteOnce]Montagem para leitura/escrita por um node de cada vez. Não significa necessariamente um único Pod.
storageClassNameEscolhe a receita oficina-postgres-gp3 e, por consequência, o driver EBS CSI.
resources.requests.storage: 2GiSolicita disco de 2 GiB. É armazenamento, não RAM.

Fluxo completo: StatefulSet → PVC → StorageClass/CSI → PV → disco EBS. Recriar o Pod normalmente reutiliza o PVC existente. Um EBS retido não equivale a backup, e uma réplica não fornece alta disponibilidade.

12. Dependências e diagnóstico

  1. Cluster ativo, nodes prontos e conectividade para baixar imagens.
  2. Driver EBS CSI instalado e com permissões AWS.
  3. Namespace oficina, ConfigMap e Secret real criados.
  4. StorageClass e StatefulSet do PostgreSQL aplicados; PVC vinculado e banco pronto.
  5. Migrations aplicadas ao banco por etapa própria.
  6. Deployment da API com imagem ECR acessível, Service e HPA com Metrics Server disponível.

Aplicar todos os arquivos de uma pasta não transforma essa lista em uma sequência com espera. Os controladores reconciliam recursos de forma assíncrona. Estes manifests do banco não executam migrations nem seed.

Comandos de consulta para acompanhar os recursos
kubectl get nodes
kubectl get pods,svc,statefulsets,deployments,hpa -n oficina
kubectl get pvc -n oficina
kubectl get pv,storageclass
